# STAR ecosystem scout: 2026 tools worth adopting

**Research snapshot:** 2026-10-12 UTC. **Scope:** public upstream documentation/repositories and STAR's current `star/next`, read with the GitHub API. **Research only:** no executable, model weights, benchmark suite, server, or Roblox experience was downloaded or contacted. No new integration is enabled by this report.

## Starting point: avoid rebuilding what STAR already has

At this snapshot `docs/research/` **does not yet exist** on `star/next`; this directory holds the new scout. Relevant pre-existing notes were read instead: [tool matrix](../../RESEARCH_TOOL_MATRIX.md) (2026-10-09), [Roblox compilers](../../ROBLOX_COMPILERS.md), [OpenGameEval plan](../../OPENGAMEEVAL_PLAN.md) (2026-10-11), [project builder](../../PROJECT_BUILDER.md), [Brain 2 practice](../../BRAIN2_CONTINUOUS_PRACTICE_20261011.md), [agent forge](../../STAR_AGENT_FORGE_RESEARCH_2026.md), [code speed](../../STAR_CODE_SPEED_RESEARCH_20261011.md), and [research roadmap](../../RESEARCH_ROADMAP.md). The six alleged local `docs/research/20261012/` notes were not available via GitHub, and were not guessed.

Code facts, independently checked against `star/next` on 2026-10-12:

- `star/project_builder.py` generates a filesystem-first Rojo project, statically validates code and retries once. `star/roblox_place.py` can invoke a pinned Rojo 7.7.1 binary; `star/roblox_pipeline.py` builds a test place and `star/roblox_cloud.py` implements scoped, approved Open Cloud operations. Thus Rojo and Open Cloud are **partly/already** present, not greenfield integrations.
- `scripts/run_luau_specs.py` runs offline Luau CLI specifications. `star/luau_lint.py` is explicitly a heuristic, not a parser or whole-project type checker. No integrated StyLua, Selene, or `luau-analyze` gate appears on the project-builder path.
- `star/providers.py` **already** sends llama.cpp `cache_prompt`, preserves earlier thinking, and manages server slots; `star/inference_benchmark.py` already measures completion timings. Optimizing the same cache fields again would duplicate work.
- `star/agent_skills.py`, `star/skill_packs/`, `star/learning.py`, `star/brain2_practice.py` and `star/eval_gate.py` already provide curated skills, approved lessons, verified practice and a non-regression gate. They are **not** evidence of model-weight self-training.
- `docs/OPENGAMEEVAL_PLAN.md` documents the benchmark but there is **no STAR OpenGameEval runner**. `star/roblox_training.py` prepares consented training data; it does not itself train weights.

The ranking is for **incremental value per engineering effort on STAR**, not an internet popularity ranking. Upstream maintenance dates are **GitHub repository `pushed_at` observations read 2026-10-12** (not a security audit or guarantee of future maintenance). Costs are rough **engineering estimates**, not measured hours or inference prices. No proprietary software licence is inferred from an open-source client's licence.

## Three highest-value incremental adoptions (concrete engineering handoff)

### P1 — **StyLua opt-in on generated Rojo modules** (smallest; implemented in companion draft PR)

Files: add `star/stylua_format.py`; change `star/project_builder.py` by an optional formatter callback and CLI `--stylua` flag; add `tests/test_stylua_project_builder.py`; document in `docs/PROJECT_BUILDER.md`.

Steps: (1) Resolve an **already-installed** `stylua` binary only when the CLI flag is present; no download or network. (2) Run bounded stdin formatting with explicit `--syntax Luau`, spaces/LF, finite timeout and output-size cap, **only** over model-generated code; leave trusted `--!strict`/dependency prefix intact. (3) Feed formatted code back through existing `validate_code` and repair attempt; never pass raw process stderr/provider details to the model or manifest. (4) Missing tool aborts before model calls or writes; default code path remains byte-identical.

Tests: real `project_builder.main` and `build_project` with fake model/formatter/binary; off means zero formatter calls and same bytes; on means formatted code + correct manifest hash; malformed Luau induces one repair; two failures block module; missing binary aborts cleanly; unsafe formatter output is revalidated and rejected. Windows-compatible, no installed formatter, network or GPU in CI. **Acceptance metric:** fixture-format success and detection of parse failures the heuristic accepted (report count). Real StyLua integration and gameplay impact remain unmeasured until a tool is available on an operator machine. **Scope:** owner opt-in only.

### P2 — **luau-analyze acceptance for build plans** (next, medium)

Files: new `star/luau_analyzer.py` (bounded offline wrapper), connect an opt-in `--analyze` in `star/project_builder.py`, tests `tests/test_luau_analyzer.py` and `tests/test_project_builder.py`, `docs/PROJECT_BUILDER.md` and `docs/ROBLOX_COMPILERS.md`. Do **not** modify `evals/` or `star/eval_*.py`.

Steps: (1) Probe explicitly selected installed `luau-analyze` with zero external downloads. (2) Stage only the generated files in a disposable temp directory; no owner workspace traversal. (3) Pass a pinned, reviewed Roblox-global type definition/config or classify missing globals as unverified; no fabricated Roblox API names. (4) Classify diagnostics deterministically, expose line/file and root cause to one controlled repair; do not run script or falsely claim Studio coverage. (5) Rerun validation after repair, never overwrite accepted source. Scope the tool to the CLI, OFF by default.

Tests: syntax and type error fixtures that existing heuristics miss, valid strict Luau, false-positive Roblox global, timeout/nonzero/stderr redaction, Windows paths, pre-existing output protection and actual `build_project` function. **Acceptance metric:** new confirmed defect detections minus false positives over a reviewed fixture set; pass/fail in two-run paired A/B. A model/Studio improvement is a hypothesis until measured.

### P3 — **DSPy/GEPA proposals behind STAR's existing fixed-set gate** (research experiment)

Files: new `star/prompt_trials.py` (candidate generator, no network by default), `tests/test_prompt_trials.py`, `docs/STAR_LEARNING.md` (or add a new `docs/research/` protocol). Reuse `star/eval_gate.py` API, not its code; never inspect, copy, or change holdouts.

Steps: (1) Curate **new**, rights-confirmed practice problems, grouped by task source to avoid answer leakage. (2) Generate at most N versioned prompt candidates under an explicit operator action; each has a content hash, optimizer/model version, token budget and no permissions. (3) Run fixed practice tests, rerun changed passes to rule out flukes, then independently run the unchanged golden gate. (4) Only offer passing candidates for separate human review; no automatic skill/agent activation, server contact or PR merge. No model is contacted in this scout.

Tests: repeated-run determinism of scoring, independent group splits, regression block, cost/attempt ceiling, all-error = incomplete, and malicious tool output cannot change verdict. **Acceptance metric:** accepted tasks / total, regressions on previously passing tasks, median latency and inference tokens **before vs after**, including confidence intervals across retries. **Estimate:** several engineer-days plus opt-in inference expense, not a measured quality gain.

## Decision, confidence and smallest next action

**Certain (source/CI observable):** the upstream repo dates/licence tags above, current STAR source integration boundaries, OpenGameEval published task counts, optional-only CLI design and pre-existing test gate. **Not established:** that any external model/tools are installed on an owner's PC, that speculative decoding helps a CPU-specific workload, that candidate prompts improve Luau correctness, or that StyLua formatting increases real game success.

**Recommendation:** merge nothing automatically; review the separate opt-in StyLua draft and require its real CI results. Next smallest action after review is to run one explicitly approved StyLua-v2.6.0 smoke fixture **outside** CI, comparing output and exit code against the fake-provider expectations. Then prioritize Luau's actual parser/type diagnostics over more prompt text, and use OpenGameEval only through its existing scoped-key plan.
