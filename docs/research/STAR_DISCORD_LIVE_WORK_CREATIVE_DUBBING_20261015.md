# STAR Intelligence: Discord Live Work Pulse, Creative Quality, and Faithful Dubbing

Research and implementation contract • 2026-10-15 • target: `star/next` via isolated draft PR

## Reality check (read before deploying)

STAR is a local-first multi-tool agent application, not a frontier model trained from scratch. Discord currently has chat, DM image critique, local/worker ComfyUI generation, voice features, a small optional Studio/Blender job receipt, opt-in Night School digest, and a static opt-in presence rotator. It does **not** have a complete audited work-event bus, advanced multi-model image jury, or anime dubbing product. This document identifies proposed engineering work; it is not a claim that it shipped.

The first contained implementation in this branch adds read-only private `/working`, `/star working`, and explicit owner-DM work questions, and a strict local producer/consumer JSON contract. **No live worker has been connected or benchmarked by this PR.** When telemetry is absent or old, the answer says so rather than fabricating a task. The bot cannot perform coding operations from messages; it can only read owner-approved evidence.

## 1. Correct the fundamental Discord problem

Today `star/discord_bot/presence.py` cycles static `Watching /star help`, `Playing STAR Intelligence` or `Watching for /ask`. These activities are intentionally safe and NOT proof of work. `lab_status.py` accepts one Studio/Blender receipt if enabled. Most direct chat previously lacked synchronized worker evidence and could answer generically.

### Proposed architecture: Proof Pulse

Producer (Night School / coding agent / model router / Studio Lab / Blender / research / image renderer)
→ a trusted **host-side supervisor** normalizes events
→ append-only local event ledger (future)
→ per-host heartbeat snapshot, atomically replaced (implemented JSON contract here)
→ owner-configured transport from Brain 1 / Brain 2 to a private aggregator (future; no bot-accessible SSH or arbitrary file path)
→ Discord private read-only status and desktop Activity Timeline
→ optionally approved, redacted snapshots/images.

A work event must have an actual task identifier, provenance source, activity type, lifecycle state, last successful operation, next scheduled operation, progress denominator if measured, UTC timestamp, and an expiry. The event must be generated by a trusted host job/controller after observing the operation; never accept the LLM's prose as proof that it worked.

Activity vocabulary: coding, studying, researching, testing, building, designing, generating, dubbing, reviewing, planning, operating. Lifecycle: queued, working, waiting, paused, completed, failed.

A snapshot is **not** a background execution engine. Stop the heartbeat when a worker exits; do not update timestamps for dead workers. Never treat an old report as a running task. Explicit '0 tasks observed' is different from a broken/unknown feed. For completed jobs, include evidence reference separately in a future ledger, not in public Discord activity.

### Implemented in this branch

- `star/discord_bot/work_status.py`: strict v1 schema, ≤12 workers / 16 KiB, plain private-data-restricted labels, finite counts, UTC times, dedup, stale states; read-only reader and trusted **single-writer** atomic producer adapter.
- `star/discord_bot/bot.py`: owner-only private `/working`, `/star working`, recognized DM questions and intercepted explicit `/ask` queries; no model-generated answer used for the work state. Existing Studio/Blender report and bot image busy flag included only when available and fresh.
- `star/discord_bot/local_config.py`: `STAR_DISCORD_WORK_STATUS=0` default and `STAR_DISCORD_WORK_REPORT` (absolute JSON path) config. No new privileges, Gateway intents, remote tools, or secrets.
- Tests: parser/field injection defenses, staleness, complete-vs-active reporting, atomic write, owner-only gateway integration and no-model-guess path.

A **trusted supervisor** must still call `publish_work_report(path, workers)` on the selected bot host. A demonstration record cannot be represented as live information; no fake seed record should be included in a release.

### Production integration gates

1. Connect a Night School adapter to its real engine attempts/state; note that a static summary does **not** imply the process is studying at this instant.
2. Connect coding/verification to tool-call events with tests, commits, runs and *outcomes*, not to a thought-stream.
3. Connect image and dubbing jobs to each render/transcription stage with cancel/error events.
4. Connect Brain 2 Studio/Blender receipts through an authenticated, **read-only**, owner-configured relay that strips secrets. The existing `lab_status.py` is a useful narrow pattern.
5. Add supervisor heartbeats and crash/reconnect tests (worker killed; stale after 180s; job that waits for owner must say 'waiting'; paused model; network cut; clock skew).
6. Add a reconciler so two hosts cannot overwrite each other's report; dedupe events and preserve provenance.
7. Stress test 1000 synthetic worker-events/min internally, while respecting the actual public Discord request rate limits. Measure report freshness, queue depth, interaction response time, rate-limit handling, CPU/RAM.
8. Complete an owner-only Discord live guild test and Windows packaged startup test before release claims.

## 2. Image generation: a specialized quality system, not random model accumulation

STAR today: `star/image_gen.py` → `star/comfy.py` FLUX.2 klein 4B distilled (four steps), text/edit/inpaint, one output; reference pinning exists, but no complete model routing, structured quality review, image-to-image evaluation loop or typography guard.

**Model strategy**

| Lane | Recommended starting point | Reason | Caveat |
|---|---|---|---|
| Draft/preview | Small quantized model that is *actually benchmarked* on installed GPU | Cheap composition iterations | Not final-quality proof |
| Fast reference/edit | Current FLUX.2 klein pipeline when it fits/offloads successfully | Reuse existing edit/pin backend | Official full 4B Base is ~13GB VRAM; don't assume 8GB GPU fits |
| Standard local | SDXL-quality validated pipeline, optional ControlNet, image reference/IP adapter where supported | Established tool ecosystem, controllable structure | Check model and checkpoint license; GPU benchmarks required |
| Higher quality/complex art | Optional separately installed newer capable model or an owner-approved hosted provider | More compute, higher output quality ceiling | Never silently upload private references |
| Finishing | High-quality constrained inpaint, anatomy detail pass, upscale, smart-crop, typography built as real text | Fix localized defects while preserving rest | Compare before/after and reject damaged unchanged regions |

A model install needs a checksum, source, checkpoint-specific license, VRAM estimate, local speed measurements, and owner approval. GPU 8GB needs budgets for UNet/transformer, text encoders, VAE, ControlNet, and concurrent apps. Respect the tradeoff: CPU/group offload saves VRAM but adds latency. Do **not** simply run four-step-distilled FLUX with 80 steps and call it 'pro'; select a trained workflow appropriate for the model.

**Aesthetic-quality gates**

Input is a structured `SceneSpec` with art direction, composition, focal hierarchy, exact palette (e.g. STAR OLED + warm-gold), characters, camera, lighting, type boundaries, forbidden traits, reference images, target output and objective geometry constraints. Do not let a free-form model rewrite approved characters or UI guidelines.

Generate 2–4 candidates if resources allow, keep seed/model/workflow and all references, then evaluate by rubric:
- Prompt subject and composition alignment (vision model).
- Character identity/pose/clothing and reference consistency, not just similarity to aesthetic samples.
- Hands/anatomy, unreadable text, duplicated limbs, warped borders, missing objects and contrast.
- Visual balance, edge alignment, crispness and legibility.
- For images containing actual GUI, keep text/icons/containers editable in Figma/React/Roblox; render-generated *concept art* is not an editable UI deliverable.
- Compare the chosen output against approved examples and previous owner corrections; unknowns go to a human review rather than invented 100/100 quality scores.

Candidate judge models can disagree: use specialized deterministic checks for exact colors, strings, constraints, dimensions, alpha bounds and reference hashes. A vision LLM is a **critic**, not proof.

Features to build: `/draw variations`, `/draw refine`, `/draw fix hands`, `/draw keep composition`, `/draw match reference`, `/draw animate` (separate video model; only when installed), `/draw why this failed` with grounded failures. Preserve approved image identity via versioned pinned reference pack. Record end-to-end latency and VRAM peak for every model.

Official starting docs: [ComfyUI workflows](https://docs.comfy.org/development/core-concepts/workflow), [FLUX.2 klein 4B Base model card](https://huggingface.co/black-forest-labs/FLUX.2-klein-base-4B), [SDXL model card](https://huggingface.co/stabilityai/stable-diffusion-xl-base-1.0), [Diffusers memory/offloading](https://huggingface.co/docs/diffusers/main/optimization/memory).

**Acceptance:** benchmark 40 owner-curated visual requests spanning avatars, UI, spritesheets, 3D references and typography; blind-review candidate A/B win rates against existing STAR, report exact defect categories, track milliseconds to first image, total generation seconds, peak VRAM, failed load rates. Never promise a quality improvement without this evidence.

## 3. STAR Dubbing Studio: authorized, frame-preserving anime/localized video

The requested experience is **subtitle-to-English dub while preserving the original animation**. “One to one” means **video stream byte-for-byte unchanged when remuxing is possible**; dialogue timing, characterization and soundtrack fidelity are separate *measured quality targets*, not guarantees of exact conversion. Only use anime/video the owner has the rights to process and voices whose use is authorized. Do not clone a recognizable voice actor without rights/permission or distribute copyrighted anime without authorization.

**Technical workflow:**

A. Import allowed video, optional Japanese subtitle `SRT/ASS`, original audio, translation glossary, rights/voice permissions. Probe using FFprobe; hash source and preserve chapters and intended original streams. Preserve original video codec stream with `-c:v copy` on final remux where container-compatible.

B. Analyze source audio: VAD, ASR (faster-whisper/WhisperX); align utterances to source subtitle offsets, corrections for punctuation/silences; pyannote diarization if speaker labels are not supplied. For stylized anime with simultaneous speech, human-correct speaker IDs and overlapping lines.

C. Create a **Scene Dialogue Map**: speaker ID, original text, subtitle text, localization variants, Japanese audio start/end and candidate English target text, proper nouns, emotional contour, allowed voice identity, overlap and laugh/shout markers. Subtitle English alone often lacks speech nuance; use source audio for intended performance.

D. Translate adaptively to comparable meaning, speech beat and target phrase length. Fit **word onsets** and total durations using iterative paraphrase instead of extreme time-stretching. Provide side-by-side original/English, one-click rewrite/revoice of a line without regenerating the whole episode.

E. Separate the original dialogue from music/SFX where feasible. Demucs is a music vocal separator, **not** a perfect dialogue/music/SFX splitter, and its upstream repo cautions that it is not actively maintained. Use isolated dialogue stems if rights holder supplies them. Preserve background atmosphere and impacts as best possible; flag bleed and artifacts for manual repair.

F. Synthesize per-character **licensed original** voices with expressive local/cloud TTS engines after source/license checks (Chatterbox Multilingual is a candidate; evaluate models and checkpoint licenses). Maintain a character voice bible with timbre, cadence, diction, age-appropriate style, emotion ranges and consistency across episodes. Voice cloning of identifiable people requires authorization.

G. Line mix: breath/attack/decay shape, silence trims, gain automation, true peak and integrated loudness checks, optional limited WSOLA/time stretch; avoid shifting source music and SFX. Video original pixels always preserved in 'soundtrack-only' mode. Optional separately approved lip-sync variant creates *modified* video and must be labeled not one-to-one.

H. QA every scene: subtitle alignment errors, target duration overshoot, overlaps, missing lines, speaker mismatch, clipping, silence, pronunciation, room-tone mismatch, translation omissions and loudness. Preserve optional original and new dub audio tracks plus updated SRT so the viewer can choose. Output includes a rights metadata note and a per-line change log.

**Tools to evaluate, not blindly bundle:** [WhisperX](https://github.com/m-bain/whisperX) for alignment, [pyannote.audio](https://github.com/pyannote/pyannote-audio) for diarization, [pyVideoTrans](https://github.com/jianchang512/pyvideotrans) for a working multi-role dubbing UX/reference (GPL-3.0: license review required), [VideoLingo](https://github.com/Huanshere/VideoLingo) for translation/timing patterns but its docs explicitly warn that 100% dubbing fidelity is not guaranteed, [Chatterbox](https://github.com/resemble-ai/chatterbox) for expressive TTS evaluation, [Demucs](https://github.com/facebookresearch/demucs) for approximate vocal/accompaniment separation, and [FFmpeg](https://ffmpeg.org/ffmpeg-filters.html) for audio timing/mixing. Evaluate F5-TTS code **and its pretrained weight license independently**; do not assume permissive code means commercial weights.

**Dubbing acceptance:** an owner-authorized 3–5 minute test with 3 voices, overlapping speech and loud music; human bilingual review for translation, voice identity and acting; detect ≥99% intended lines present, no unexpected video-frame edits, voice segment timing metrics and objective loudness compliance. Report residual overlap and masking artifacts. A realistic human target is **high-quality dubbed adaptation**, not perfect reproduction by an automatic script.

## 4. Distinctive experiments with measurable advantages

### Proof-carrying AI work cards

Every completed STAR task can show the original request, immutable input fingerprint, which model/tools ran, files/patches changed, test IDs and evidence, reviewer feedback and exact differences. `/work proof` opens links to the *evidence*, never unverified model prose. STAR detects 'I am researching' when no search tool ran and refuses that self-description.

### Creative Memory: rejected vs accepted examples

Build versioned visual preference tests with owner-approved good/bad pairs. Detect recurrent mistakes (misaligned Roblox GUI labels, missing character hands, off-theme palettes, inconsistent mascot details) before release. Corrections become regression cases *after explicit owner approval*, not silent model self-training. Split the dataset into training/development/blind evaluation slices to guard against the model overfitting its own tests.

### Self-debugging with counterfactual replay

Before touching a Roblox project, a planner predicts the failure modes and required tests; STAR runs those tests. A second reviewer must prove the first agent's successful work against execution logs, screenshot comparisons and per-platform checks. 'This is going to fail' is a probabilistic risk estimate, not guaranteed future knowledge. The most useful output is *a reproducible failing test and a precise fix*.

### Replayable render plans

Cache media generation graphs, audio segment timestamps, input hashes and project references so a single bad hand or dubbed line re-runs only the dependent node rather than regenerating an entire illustration or episode. Explicitly invalidate caches when model/checkpoint/license or references change. Track actual saved compute and byte-for-byte unchanged regions.

### Budget-aware model orchestra

Route according to job type and real hardware pressure. Run cheap local draft agents for planning and deterministic critique; reserve powerful/high-VRAM work for clearly justified scenes, keep model cold-start telemetry and contention controls, and prefer one high-quality proof over eight low-quality attempts. Report actual cost/latency win rate versus a single-agent baseline.

### Discord as a control *dashboard* first

Offer owner-only Ask, Work Pulse, Proof, Studio Lab, Image QA, Learning Digest, and Dubbing preview in one thoughtful compact layout. Safe future command actions must go through a separately audited explicit approval protocol; never let a Discord DM become arbitrary shell, Studio, GitHub or payment access just because the sender is the owner.

## 5. Engineering gates and nonclaims

**Current branch scope:** only worker status read/publish contract, bot routes, settings, tests, and this research. No installs, GPU models, dubbing exports, API keys, server changes, Night School producer connection, Discord token use, or background audio capture. Owner must review and explicitly enable the settings. Do not merge to main or ship an installer until GitHub checks and live acceptance confirm behavior.

**Security:** owner ID + approved guild/channel, ephemeral slash replies, no secret IDs/tokens/paths in public output, no privileged message-content intent, no automatic upload of private art, no unconsented recording/dubbing, bounded files, symlink and size checks, SHA-verified evidence where available, stale-report fail-closed behavior.

**Objective success metrics:** factual work-state correctness in injected known-event tests; stale-state false-running count **zero**; median and p95 Discord time to first reply; percentage of worker actions with evidence receipts; model-to-tool claim consistency; visual blind win rate; GPU peak memory/seconds; dubbing line coverage and sync error distributions; tester ratings with human signoff. Neither count of integrated models nor amount of generated content proves intelligence.
