# Security audit 2026-10-13 (defensive, with fixes)

Scope: `star/next` @ `64c1982`. This was a source review of these areas:
- web fetch and search
- workspace file tools
- subprocess and dynamic-code use
- the Luau and Studio execution paths
- how tool results and prompt injection are handled
- secrets and redaction
- the Discord bot
- screen-capture consent
- the Qt WebEngine shell
- Python and frontend dependencies

Where a finding was reproduced, the reproduction is named. Everything else comes from reading the code. This is not a penetration test and does not claim to be exhaustive. Earlier reviews: `docs/SECURITY_REVIEW_PR40_20261011.md`, `docs/SECURITY_REVIEW_2_20261012.md`.

Exploit detail is kept to what a maintainer needs in order to verify a fix. For open items, only the location and the class of issue are given.

### H-1 (High): Windows path spellings bypass the workspace's protected names (fixed, #313)

**What happened.** Windows drops trailing dots and spaces when it opens a path. `Workspace.resolve` compared the resolved, not-yet-existing path against the protected names (`.git`, `.github`, `.env`, `.ssh`, key suffixes). It therefore accepted `.git./config`, and the write then landed in `.git/config`.

**Reproduced** on Windows 11: `workspace_write` created `.git/config`, `.github/workflows/*.yml`, `.env`, `x.key` and `b.pem` under protected names.

**Impact.** With workspace edit mode on, a model steered by injected text could write git configuration that runs a command on the owner's next git operation.

**Fix:**
- Every requested path component is checked before the file system is touched. A component is refused if it ends in a dot or space, contains `:` or another character Windows forbids, or is a device name.
- Protected names are checked on both the requested spelling and the resolved file.
- `.env.*` (templates excepted), `.netrc` and `.git-credentials` are now protected too.

**Regression test:** `tests/test_workspace_path_spellings.py`.

### M-1 (Medium): web content could steer `execute_luau` in the same turn (fixed, #314)

**What happened.** When the owner has enabled Studio edit and full Luau (both off by default), one agent turn could read a web page and then call `execute_luau`. Nothing tied the arrival of untrusted text to the code-execution tool; only system-prompt wording stood in the way. `execute_luau` is unrestricted inside Studio (`policy.py` says so), and the undo wrapper does not confine code.

**Fix.** Once a tool that returns third-party text has returned in a turn, `execute_luau` is refused for the rest of that turn. Those tools are `star_web_fetch`, `star_web_search`, MCP registry search, and any MCP gateway or registry tool.

**Regression test:** `tests/test_luau_after_untrusted.py`.

**Residual:**
- `multi_edit` and playtest input are still allowed after a web read. They write only scripts and inputs the edit journal records, but they remain a path for a model influenced by web content.
- Owner-attached reference sections (documents, notes) do not set the flag.
- A per-call owner confirmation for `execute_luau` would be stronger. It needs a UI round trip and is left as a follow-up.

### L-1 to L-3: web fetch hardening (fixed, #315)

- **L-1:** the configured search-gateway exception, the one private address a fetch may reach, also applied to redirect targets. A public page could therefore bounce a fetch onto the LAN gateway. The gateway still requires its bearer key, so this was Low. The exception now applies only to the URL the request named.
- **L-2:** page text, title or URL could contain the closing frame marker and end the "untrusted data" frame early. Tool results already travel as `role: tool` messages, so the frame is a second layer. The markers are now defanged inside page data.
- **L-3:** an unknown declared `charset` raised `LookupError` out of a tool documented never to raise. It now falls back to utf-8.
- **Checked, already safe:** the IPv4-compatible (`::a.b.c.d`) and NAT64 (`64:ff9b::/96`) spellings of private IPv4 addresses are refused through `is_reserved`. New tests pin this.

**Regression test:** `tests/test_web_fetch_hardening.py`.

### L-4: FFmpeg protocol whitelist for Discord audio (fixed, #316)

Audio attachments, which can come from other users' messages through "Ask STAR about this", were decoded with no protocol whitelist. Current FFmpeg builds already refuse playlist and concat inputs on a pipe (checked against a 2026 build). `-protocol_whitelist pipe` now protects older builds as well. **Regression test:** `tests/test_discord_bot.py::test_ffmpeg_reads_only_stdin`.

### L-5: redaction missed common key formats (fixed, #318)

`redact_text` runs over transcripts, answers, memory events and tool errors. It now also recognises:
- Discord bot tokens and `Authorization: Bot`
- `hf_`, `AKIA`, `AIza`, `xox*-` and `glpat-` keys
- Stripe-style live and test keys

Chat history in `conversations.sqlite3` is intentionally stored unredacted on the owner's PC.

### L-6 (open): sent screenshots outlive the capture folder's limit

The "Look at my screen" folder keeps at most 40 captures. A capture the owner then sends, like any attached picture, is copied into the knowledge artifact store with no retention limit. The data stays local, but it is kept longer than the screen-capture module documents.

**Suggested fix:** skip artifact ingestion for files under the capture folder, or give those copies a retention limit.

### L-7 (open): the project builder's forbidden-API check is token-based

The validator for generated ModuleScripts can be bypassed by Luau that reaches a forbidden service without naming it directly. STAR never runs this code; it is written to disk for the owner. The check should be read as a lint, not a sandbox.

**Suggested fix:** an allowlist of methods, as `studio_milestones.validate_check` already uses.

### L-8 (open): model-written Luau on the servers shares a user with the model services

Night School and the eval sandbox run model answers in the standalone Luau VM, which has resource limits and an allowlisted environment. They run as the same account as the model servers and without network isolation.

**Suggested fix:** a dedicated sandbox user plus `unshare -n` or `bwrap --unshare-all`.

### L-9 (open): subframe navigations are not filtered

The main frame may load only the packaged `index.html`, but every subframe navigation is accepted.

**Settled by experiment** (PySide6 6.12, offscreen, using a copy of the page class). This closes the WebChannel question left open in review 2:
- The bridge (`qt.webChannelTransport`) exists only in the main frame.
- Remote iframes do not load at default settings. When forced to load, they get no transport, and `parent.qt` throws a SecurityError.
- Only a same-origin local or `srcdoc` iframe could reach the bridge. Creating one already requires injecting HTML into the main page.

The desktop UI creates no iframes.

**Suggested fix:** give subframes the same index-only rule as the main frame.

### L-10 (open): no Content-Security-Policy

No injection sink was found:
- react-markdown runs without raw HTML.
- No `dangerouslySetInnerHTML` is used.
- Links are limited to http, https and mailto.
- Images are replaced with a text note.

A CSP would still limit the damage of a future one, and it would harden the `consent: true` screenshot flag, which the page itself supplies.

**Suggested fix:** a desktop CSP tested on both the desktop and the website builds: `default-src 'self'; frame-src 'self'; object-src 'none'; base-uri 'none'`, plus hashes for any inline script.

### L-11 (open): dev-only test tooling advisories

`pnpm audit --prod` is clean. The full audit flags tinypool 1.1.1 (two critical advisories) and vitest / @vitest/mocker 3.2.7 (moderate), all pulled in through vitest. They run only on the project's own tests, locally and in CI, and never ship.

**Suggested fix:** move `vitest` to `^4.1.11`. This is a major upgrade: it resolves cleanly with no peer warnings, but the frontend suite has not been run under vitest 4 yet, so it gets its own PR.

### L-12 (open, blocked upstream): pynacl 1.5.0

PyNaCl 1.5.0 has advisory CVE-2025-69277 (fixed in 1.6.2). The flaw is in libsodium's ed25519 point-validation check. discord.py voice uses the secretbox/AEAD encryption functions, not that check.

The current discord.py (2.7.1) pins `PyNaCl<1.6`, so no safe bump exists yet. Upgrade once discord.py lifts the cap.

## Info (no change needed or by design)

- **Studio `http_get`** is offered as a read tool. The Studio connector itself only fetches Roblox documentation URLs, and STAR does not add its own allowlist. If a future connector widens that list, add a host check in `policy.enforce`.
- **The Luau undo wrapper** in `studio_loop.py` records undo; it is not a confinement boundary. A broken receipt fails safe: the edit is marked unconfirmed and later edits are blocked.
- **The blank-place test** accepts an unsaved place carrying the `StarSandbox` attribute, and that attribute can be saved in a local file. A per-install HMAC marker would be stronger.
- **Workbench program denylist** (`server/workbench/app.py`): convenience only. The bwrap sandbox and the token are the real boundary. The token is also accepted in the URL path, and access logs are off.
- **`star_web_fetch` and `star_web_search` can exfiltrate data by design.** A GET request to any public URL can carry data in its query string. The tools have no access to keys, but the model's context can leak this way.
- **Discord bot tracebacks:** the bot logs tracebacks to its console. Keys travel in headers, so no key text was found in those messages.
- **New-window requests** (`window.open`, `target=_blank`) are raised by Qt but never opened. That is safe, though clicked Markdown links may do nothing in the desktop app.
- **Remote debugging:** Qt honours `QTWEBENGINE_REMOTE_DEBUGGING` and `QTWEBENGINE_CHROMIUM_FLAGS` from the environment. Only `scripts/packaged_smoke.py` sets them. A release build could clear them at startup.
- **Release builds resolve dependency ranges at build time:** there is no Python lockfile, and the frontend lockfile is untracked. `dependency-audit.yml` audits only `requirements.txt`. Suggested: audit every requirements file plus `npm audit --omit=dev`.
- **Studio screenshots:** the model may take Studio screenshots through the connector; camera moves require edit mode. Desktop capture is not reachable from any model tool.

## Protections verified

- **Web fetch:** each request is pinned to a resolved IP and checked again on every redirect. Requests carry no proxy and no credentials, use limited ports, size and time, and accept only text content types.
- **Web search:** fixed provider hosts and https-only result URLs. Keys travel in headers, never in the query string.
- **Workspace:** `resolve(strict=True)` blocks symlinks and `..` escapes, writes are atomic through a unique temp file, and `workspace_write` requires edit mode.
- **No unsafe dynamic code:** no `shell=True` anywhere, and every subprocess takes an argument list. FFmpeg and ffprobe paths are absolute, so a value starting with `-` cannot be injected as an option. There is no `pickle`, `yaml.load`, `marshal`, `eval` or `exec` on untrusted input; `compile()` is used only as a syntax check.
- **Studio policy:** `policy.enforce` re-validates the tool name, the exact `studio_id`, the Edit DataModel and the schema on every call. Unknown connector tools are never offered. `execute_luau` requires both the edit and the Luau switch.
- **Eval Luau:** source is base64-encoded inside a quoted heredoc, wrapped in a long bracket whose level the code cannot close. It runs in an allowlisted environment with no `getfenv`/`setfenv`, `loadstring`, `require`, `debug` or `io`.
- **Roblox Open Cloud:** fixed hosts, redirects off, and an owner click is required for publish and `run_luau`.
- **Discord access:** owner checked by numeric ID (fail-closed), guild and channel allowlists, and a per-user sliding-window rate limit. Mentions are disabled on every send. Discord model calls get no tools at all.
- **Discord screenshots:** off by default, need a single-use 60-second owner button, and are not saved.
- **Desktop screenshots:** need the consent dialog in the UI plus a literal `consent: true` in the request. No timer or model tool can trigger a capture.
- **Secrets:** stored in the Windows credential store. The settings payload sent to the page carries booleans only. The diagnostics bundle is allowlist-only. There is no crash handler that dumps state. Server keys are compared with `hmac.compare_digest`.

**Qt shell and frontend:**
- Main-frame navigation is limited to the packaged index.
- External links open only for https URLs on four hosts.
- `LocalContentCanAccessRemoteUrls` is false.
- Microphone and geolocation permission requests are never granted, and clipboard read is denied.
- No DevTools are attached in shipped code.
- The bridge uses a fixed action allowlist with a 100 KB request limit, and file reads are limited to files the user picked.

**Dependencies** (pip-audit 2.10.1 on all `requirements*.txt`; pnpm 11 audit):
- No known vulnerabilities in the core, desktop, voice or dev Python requirements, nor in the production frontend dependency tree.
