# STAR Roblox tycoon template

A six-plot, server-authoritative tycoon starter built from source. Every player receives an unoccupied plot after their save is opened. The starter dropper is free; its physical parts fall onto a collector that awards cash. Three purchase pads unlock in order. Rebirth clears purchased droppers and cash, preserves the starter, and increases future income.

## Build and inspect

- Install [Rojo](https://rojo.space/) and run `rojo build default.project.json -o tycoon.rbxlx` from this folder, or `rojo serve default.project.json` while connected to a **new, disposable** Roblox Studio place.
- The parts, plots, pads and collectors are generated by `ServerScriptService/Plots.luau` at runtime; the Rojo project contains scripts, not a prebuilt map.
- For STAR's scripts-only headless place pipeline, use `python -m star.roblox_pipeline --source examples/roblox-templates/tycoon`. Publishing or executing its Luau specs requires an owner-approved **private test experience** under the existing STAR safeguards; this command alone does not authorize publication.
- `ServerScriptService/Tests/Economy.spec.luau` uses the STAR harness's `*.spec` format. It checks immutable transitions, validated purchases, saved-data normalization, collection, cap configuration and rebirth. `pytest -q tests/test_roblox_tycoon_template.py` checks the offline source and Rojo layout.

## Economy and world

`ReplicatedStorage/Shared/Economy.luau` is the **single source of truth** for item order, prices, production intervals, part cap, cash per part, rebirth price and multiplier. The client reads it only to display prices and balances; it cannot change the server's copy or award money. The free starter generates $10 per part, then purchases cost $100, $500 and $1,800. The initial rebirth requires the final dropper and $4,000; every rebirth adds 0.5x income and increases the next rebirth cost by $1,500. A maximum of 36 uncollected parts can exist on each plot; stale parts are destroyed after 20 seconds.

Every plot and its purchase pads are created on the **server**. ProximityPrompt callbacks check the triggering player against the currently claimed plot. The server applies `Economy.buy` to its own state: unknown ids, duplicates, skipped prerequisites and insufficient cash are refused without mutation. All cash parts are created and tracked server-side, with server-owned physics. The collector refuses anything not present in its per-plot active-part table, removing each part before crediting to prevent double payment. Rebirth destroys outstanding parts, shuts down old dropper loops and rebuilds only the starter.

## Data and trust rules

`PlayerData.luau` uses `DataStoreService:UpdateAsync` to acquire a per-player expiring session lease, and to save **cash, owned ids, rebirths** and the lease. Calls are wrapped in `pcall` and retried with bounded backoff. Saves are serialized within a server; older sessions cannot overwrite a different lease holder's progress. Ownership is restored only for known items whose prerequisites are present. Failure to open a save is **fail-closed** (no temporary balance that could overwrite real progress). On leave/shutdown the plot is released and a final save removes the lease; crashes leave a lease that expires in three minutes. Autosaves renew it once per minute.

Do not trust client prices, currency, purchased flags, tool requests, touch-generated instances or player attributes as an authoritative source. Do not add a client-to-server purchase or credit remote without the equivalent server checks. No real keys, personal ids, production experiences or user data belong in this template. No code here should publish a place or bypass STAR's approval or safety policies. Roblox DataStores require a **published test experience**, and Studio API Services access must be enabled to exercise persistence in Studio. Use a distinct datastore name when adapting this for a real game; add operational monitoring and load testing before production.

There are six plots. Configure the test place to allow at most six concurrent players; a seventh player receives a capacity message. This is a teaching template, not a fully scaled datastore/session-management service.

## Studio playtest checklist

- [ ] Run with two clients; each receives a different plot, respawns there, and cannot purchase on the other's pad.
- [ ] On first join, confirm a starter dropper exists, drops fall onto the green collector, and only one credit is awarded per part.
- [ ] Block collection temporarily; no plot exceeds 36 active money parts, and old parts disappear after 20 seconds.
- [ ] Confirm purchase pads become enabled **only** after the predecessor is bought; insufficient cash and repeat purchases do not debit.
- [ ] Collect enough for the next three purchases; check displayed costs match the shared catalog and saved ownership.
- [ ] Confirm rebirth stays disabled until the last dropper is owned and the rebirth cost is met.
- [ ] Rebirth; observe all old money parts and paid droppers removed, starter returned, cash zero, rebirths incremented and future cash per part increased.
- [ ] Leave and rejoin; cash, owned items and rebirth count persist, while the previous plot becomes available to another player.
- [ ] Simulate datastore errors and overlapping sessions in a disposable test experience; opening must fail closed, stale saves must be rejected, and retries must not double-award purchases.
- [ ] Close a test server with active players; verify a final save and that the next session can acquire its data. After a crash, allow the lease to expire before reopening.
- [ ] Run the Luau spec harness in a private test place and the offline pytest suite; neither is a substitute for multiplayer/persistence playtesting.
